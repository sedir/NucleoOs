# NucleoOS Internationalization (i18n)

The native UI ships Italian, English, Spanish, French, German and **Brazilian Portuguese**
(`it`, `en`, `es`, `fr`, `de`, `pt`). The web OS additionally supports Simplified Chinese (`zh`).
English is the base and the fallback for missing translations. Portuguese is a flash catalog on
native screens and a reproducible edition layer over the pinned nucleo-webos build on the web.
ANIMA understands Portuguese device commands and a small reviewed exact-question FAQ offline;
its larger semantic knowledge corpus remains Italian/English. Offline TTS includes Portuguese;
browser offline dictation still uses the existing Italian/English Vosk models. See
[anima-pt.md](anima-pt.md) for the shipped behavior and remaining limits.

## Simplified Chinese (`zh`)

The web OS also speaks Simplified Chinese: every catalog (`*.zh.json`), the words modules keep in code
(wizard, pairing, copilot, key manager, ANIMA, Paint…) and the manual. It is a **browser-only** language:
the firmware stores and shows only the five languages above (the TFT font is Latin-only), and every
released firmware turns an unknown code into `en`. So the web OS keeps Chinese in the browser *over* the
device's English: it tells the device `en` (`I18N.deviceLang()`), and an `en` coming back from the device
keeps the browser on Chinese (`I18N.fromDevice()`); any other language chosen on the device wins. No
firmware change is needed, on any release.

Translations are made and reviewed in the shared web OS repository (`nucleo-webos`, `docs/languages.md`),
which also has the guards: same HTML tags and `{placeholders}` as the English, no invisible characters,
every five-language table in code carrying `zh`. The copy in this repository (`web/shell/`, `apps/`) is
generated and locked by `webos.lock`: corrections to a Chinese string go to `nucleo-webos`, or as a PR here
that touches only the `*.zh.json` files, which the maintainer carries over. The Chinese started from a
community contribution.

## Why centralized

The OS is a desktop **shell** plus ~40 **apps**, each loaded in an iframe from `/apps/<id>/`. Before
this system there were three incompatible patterns (a per-app string table in Settings, inline
`en ? '…' : '…'` ternaries in onboarding/copilot, and hardcoded Italian in the shell). One engine
replaces all of that: a single language signal, one persistence path, one way to translate a string.

Everything runs **in the browser**. The Cardputer only serves small static JSON catalogs, so the
device cost is ~0 — consistent with the no-PSRAM, web-native design.

## The pieces

| File | Role |
|------|------|
| `web/shell/nucleo-i18n.js` | The engine. Served at the OS root → importable as `/nucleo-i18n.js` from the shell **and every app iframe** (same origin). |
| `web/shell/i18n/core.{it,en,es,fr,de}.json` | Shared OS vocabulary (Save, Cancel, Open, File, …). Merged **under every namespace**, so any app gets it for free. |
| `web/shell/i18n/shell.{it,en,es,fr,de}.json` | The shell chrome (Start menu, taskbar, dialogs, toasts, context menus). |
| `apps/<id>/www/i18n.{it,en,es,fr,de}.json` | Per-app catalog. Co-located with the app; resolved automatically as `/apps/<id>/i18n.<lang>.json`. |
| `tools/i18n-check.mjs` | The gate (`npm run i18n:gate`): JSON validity, strict key-set parity for the required languages (`en`, `it`), no stray keys + a coverage report for the tier-2 ones (`es`, `fr`, `de` → `web/shell/i18n/coverage.json`), plural shape, placeholder parity, and that every `data-i18n` key referenced in HTML exists. |

### The language signal

The active language is the existing OS-wide key `localStorage['anima.lang']` (`'it' | 'en' | 'es' |
'fr' | 'de'`). It is mirrored from the canonical store `/system/config/settings.json → ui.language` by
the shell on every load, and written there by the Settings picker. The engine reads `anima.lang`,
falling back to `<html lang>`, then the base language `en` — deliberately **no** `navigator.language`
auto-detect: the OS is English-first and the first-run wizard asks for the language.

### Live, OS-wide switching (no reload)

Changing the language in **Settings** (or the copilot toggle, or onboarding) writes `anima.lang`.
That fires a `storage` event in **every other same-origin document** — i.e. all the open app iframes
— and the engine in each repaints itself. The setting frame and the shell are updated directly via
`setLang()` + a `set-language` postMessage. Net effect: pick a language anywhere and the whole OS,
including every open window, switches instantly. `<html lang>`/`dir` are kept in sync for CSS and a11y.

## Using it in an app

The smallest correct integration is **annotate the HTML + one bootstrap line + two catalog files**.

1. Annotate static markup (declarative — the engine fills these, and a MutationObserver also
   translates any annotated element the app adds later, so you rarely call `apply()` yourself):

   ```html
   <h1 data-i18n="title">Titolo</h1>
   <input data-i18n-attr="placeholder:search_ph;title:hint" placeholder="Cerca">
   <p data-i18n-html="rich">…</p>                 <!-- innerHTML, for trusted catalog strings -->
   <span data-i18n="left" data-i18n-args='{"n":3}'>…</span>   <!-- interpolation vars -->
   ```
   If an element has an icon **and** a label, wrap only the label: `<button><svg…></svg><span data-i18n="x">…</span></button>`.

2. Bootstrap once. If the app's main script is a module, import the engine and use the bound `t`:

   ```js
   import I18N from '/nucleo-i18n.js';      // absolute, NO /www/
   const t = await I18N.init('myapp');      // loads core + myapp catalogs, paints, observes, live-switches
   el.textContent = t('greeting', { name }); // dynamic strings built in JS
   I18N.onChange(() => repaintImperativeBits());
   ```
   If it is **not** a module, add a self-contained module near the end of `<body>` — no coordination needed:

   ```html
   <script type="module">import I18N from '/nucleo-i18n.js'; await I18N.init('myapp');</script>
   ```
   and annotate the strings inside your JS `innerHTML` templates with `data-i18n` so the observer
   translates them on insertion.

3. Write `apps/myapp/www/i18n.en.json` and `i18n.it.json` with the **same key set** (the gate enforces
   it), plus `i18n.es.json`, `i18n.fr.json` and `i18n.de.json` (tier-2: a missing key falls back to
   English, but every shipped catalog is at 100% coverage — keep it there). Don't redefine generic
   words — reference `core` keys (`save`, `open`, `cancel`, `file`, …) directly; only add keys for
   app-specific text.

### `t()` semantics

- Lookup order: app namespace → `core` → the key itself (never blank; a visible raw key flags a gap).
- `t('items', { count })` selects a plural form via `Intl.PluralRules` when the value is
  `{ "one": "…", "other": "…" }`.
- `{name}` placeholders are interpolated from `vars`.

### Locale-correct formatting

Use the engine's `Intl` helpers instead of hand-formatting, so dates/numbers follow the language:
`I18N.fmtDate(d)`, `fmtTime`, `fmtDateTime`, `fmtNumber(n)`, `fmtBytes(n)`, `fmtRelative(-3,'minute')`,
`fmtList([...])`.

## Adding a language

1. Add a row to `LANGS` in `web/shell/nucleo-i18n.js` (`{ code, label, flag, dir, locale }`). The
   Settings and onboarding pickers render from this list, so the option appears automatically.
2. Add `core.<lang>.json` and `shell.<lang>.json`, then `apps/<id>/i18n.<lang>.json` per app.
3. `npm run i18n:gate` until green. (Add the code to `LANGS` — required, strict parity — or
   `EXTRA_LANGS` — tier-2, partial allowed — in `tools/i18n-check.mjs` to match.)

RTL is anticipated: set `dir: 'rtl'` in the `LANGS` row and the engine flips `<html dir>`.

## Build & deploy notes

- Catalogs and the engine are precached by the service worker (`web/shell/sw.js`) so the chrome is
  translatable offline. **Bump the `CACHE` version in `sw.js` whenever a shell asset changes**, or the
  browser serves the stale cached copy (this is the #1 "my change didn't show up" trap).
- Regenerate `.gz` siblings after editing served assets: `node tools/gzip-assets.mjs web/shell apps`.
- The simulator (`node tools/serve-shell.mjs`, port 5599) serves all of this exactly like the device
  (`/<asset>` → `web/shell`, `/apps/<id>/x` → `apps/<id>/www/x`).

## Native (on-device) UI — same language, one signal

The **native C/C++ UI** (the on-TFT launcher + apps in `firmware/`) shares the SAME language signal as
the web: `settings.json → ui.language`. There is no second setting and no per-surface fork — set the
language on the device or in the browser and the WHOLE system follows.

- **Engine** (`firmware/components/nucleo_storage/nucleo_i18n.{c,h}`): a few bytes of RAM — the active
  language code, clamped to `{it,en,es,fr,de,pt}` (anything else → `en`; default `en` on a fresh device).
  `TR5(it, en, es, fr, de)` / `nucleo_tr5()` pick the right flash literal for all five languages at the
  call site (zero per-string RAM). The older two-literal `TR(it, en)` / `nucleo_tr()` paints Italian only
  for `it` and **English for every other code**, so a Spanish/French/German user sees English — never
  Italian — on a string that has no five-language form yet. `nucleo_i18n_lang()` returns the code;
  `nucleo_i18n_is_en()` is a hot accessor. `nucleo_i18n_load()` reads `ui.language` at boot;
  `nucleo_i18n_set_lang()` sets it AND persists `ui.language` (read-modify-write, other keys kept);
  `nucleo_i18n_set_en()` is the IT/EN shorthand for it.
- **Launcher titles + categories are in all five languages.** Categories are translated in `node_label()`
  (`launcher_render.cpp`). App titles come from a single central table `APP_NAME_TR`
  (`id → {it, en, es, fr, de}`, ASCII only — the on-TFT font has no accented glyphs) — the one place that
  localizes the app names without touching the individual registrations, zero per-app RAM, picked live at
  render. Spotlight search matches the title in ANY of the five languages. Proper-noun apps (ANIMA,
  Mail, SSH, Pong, …) fall through to their own name. App `desc` is not rendered, so it isn't translated.
- **Picking the language on the device.** Native Settings ▸ Language cycles all five (`app_wifi.cpp`); the
  first-run wizard's language step offers English / Italiano only (`nucleo_setup.c`), so the other three
  are chosen afterwards in Settings (native or web).
- **ANIMA stays IT/EN.** The on-device NL engine understands Italian + English (`nucleo_anima.h`), and the
  offline TTS voice packs exist for `it` and `en` only (`/sd/data/tts/<lang>/`, see [`tts.md`](tts.md)).

### Catalog languages (pt-BR)

A sixth on-device language does not add a sixth argument to ~2,700 call sites. **Portuguese (Brazil), code
`pt`,** is a *catalog language*: one table keyed by the **English** literal of each `TR` / `TR5` / local picker
call (`L5`, `H5`, `W5`, `PT`, `UT`). With `pt` active, `nucleo_tr()` / `nucleo_tr5()` hash the English bytes
(FNV-1a), binary-search the flash table (`nucleo_i18n_catalog.h`) and return the translation; a string the
catalog lacks falls back to English. Zero RAM, no call site touched.

- **Source of truth:** `tools/native-i18n/pt.json` (English → Portuguese, ASCII only like every TFT string).
- **Generated:** `firmware/components/nucleo_storage/nucleo_i18n_pt.c` — never edit by hand.
- **Workflow:** `node tools/native-i18n/native-i18n.mjs extract pt` lists every English string with the room it
  has; edit `pt.json`; `node tools/native-i18n/native-i18n.mjs gen pt` validates and regenerates;
  `npm run i18n:native` (`gen pt --check`) fails on a missing string, a changed `%` conversion, a non-ASCII
  character, a translation longer than the longest variant already shipped at that call site (+2; the hint
  bar's 39 glyphs are strict), or a stale table. A new `TR5(...)` in the firmware therefore needs its `pt.json`
  line before the check passes.
- **Also in pt:** Settings ▸ Language and the first-run wizard list *Portugues*; the launcher's app names have
  a `pt` column in `APP_NAME_TR` (Spotlight searches all six); the launcher date uses Portuguese day/month
  abbreviations; the Wi-Fi regulatory country is `BR`; ANIMA's LLM paths are told to reply in Brazilian
  Portuguese (`nucleo_anima_lang_name`).
- **Static tables:** mark English entries with `I18N_EN("English", "Italian")` (the optional second
  literal supplies the existing layout budget), then translate their selected display value with
  `nucleo_tr_en()` or `nucleo_tr()`. The native gate extracts these too. This covers ANIMA, SSH,
  NucleoLink, Clock and the security-tool guides that previously bypassed the catalog.
- **Games:** their separate text packs remain outside pt-BR coverage.
- **Web:** this edition ships pt-BR through the reproducible `tools/webos-pt` layer over the pinned
  nucleo-webos build. Its catalogs are required by `i18n:gate`; language sync sends `pt` to the device.
  See [ANIMA pt](anima-pt.md) for offline knowledge and dictation limits.

### Cross-surface live sync (set anywhere → everything switches)

`settings.json → ui.language` is the single source of truth; both surfaces read AND write it, and a change
on either side is pushed to the other **live**:

- **`GET/POST /api/lang`** (`nucleo_httpd.c`). `POST {"lang":"it"|"en"|"es"|"fr"|"de"}` (paired) calls
  `nucleo_i18n_set_lang()`, which persists the code verbatim, bumps a **generation counter**
  (`nucleo_i18n_gen()`), and fires an on-change hook that publishes a `system.language` event onto the bus.
- **WebSocket broadcast.** The event-bus → `/ws` sink pushes `system.language` to every connected browser;
  the shell (`shell.js`) calls `I18N.setLang()` and the whole web OS repaints with no reload.
- **Web → device.** The shell's `set-language` handler `POST`s `/api/lang`, so a change made in web
  Settings updates the native flag + persists once, canonically, on the device. Loop-safe: the device only
  re-broadcasts on an ACTUAL change, so an echo is a no-op.
- **Device → native repaint.** A web-side change flips the flag from the httpd task; the app main loop
  (`nucleo_app.cpp`) watches `nucleo_i18n_gen()` and forces the launcher to repaint in the new language
  live. The native language controls (`app_wifi` Settings ▸ Language via `nucleo_i18n_set_lang()`;
  `app_link`, `app_anima` and the first-run wizard via `nucleo_i18n_set_en()`) go through the same setter,
  so a change made ON the device broadcasts to the browsers too.

The native track needs a **firmware flash** to ship (`tools/release.ps1` / OTA) — the web catalogs ship
with an SD sync. Build/gate freely; flash only when asked.
